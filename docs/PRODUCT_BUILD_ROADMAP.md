# MNEME — Product Build Roadmap (grounded, Rust 1.86-stable)
> Generated 2026-06-22 from a 12-agent grounded planning pass (9 product architects + shared-infra extraction + adversarial dependency audit + roadmap synthesis). Every API call verified against the tree; every crate audited against the Rust 1.86.0 pin.

## Core strategy
Do **not** build 9 standalone products. Build a shared **Wave 0 foundation** once; each product then reduces to product-specific commands + screens. The keystone: lift MTL + Shapley out of the `mneme-cli` binary into a reusable off-TCB `mneme-receipts` library (6 of 9 products are blocked on this).

## Hard MSRV pins (cut-lines — silent `cargo update` will break these)
- **redb (claimed 2.x / 2.1 / 4.1, asserted 1.86-stable)** — MSRV violation. redb 4.1.0/4.0.0 and 3.x ALL declare rust-version 1.89 (> 1.86). The Two-Brain Sync plan literally pins 'redb 4.1' which CANNOT build on 1.86. The other plans say '2.x'/'2.1' and assert 1.86-clean, but plain 'redb = 2' or 'redb = 2.x' resolves to the 2.6.x tail (2.6.0+ MSRV 1.85 — ok) yet a careless '^2' that picks up nothing newer is fine while '4.1' is fatal. The blanket 'builds clean on 1.86' claim is FALSE for the resolved-latest. Must hard-pin.
  - **Fix:** Pin exactly: redb = "=2.6.3" (last release with MSRV 1.85, still MIT OR Apache-2.0, pure-Rust, MVCC single-file). Do NOT allow 3.x/4.x until the workspace MSRV moves past 1.89. Alternative pure-Rust KV if a 1.86 cap must hold long-term: sled 0.34 (but it is effectively unmaintained) or fjall — otherwise stay on redb 2.6.3.
- **keyring 3.x (MNEME Vault)** — Version field is stale/ambiguous and risks MSRV drift. Current keyring is 4.1.2 with MSRV 1.88 (> 1.86). A bare 'keyring = 3' is safe today (3.x MSRV 1.75), but the plan writes '3.x' loosely and the crate has already shipped a 4.x line that breaks 1.86. Without an exact pin, a future 'cargo update' across the 3->4 boundary breaks the build. Flagged as MSRV-fragile.
  - **Fix:** Pin keyring = "=3.6.3" (MSRV 1.75, MIT OR Apache-2.0, maintained, supports macOS Keychain / Windows Credential Manager / libsecret as the plan needs). Hold off on 4.x until MSRV >= 1.88.
- **rmcp 0.1 / 0.x (Consent Vault Phase 6, MNEME Vault, Portable Brain)** — Stale/incorrect version pin + churn risk + the plans themselves flag MSRV uncertainty. The pinned '0.1.x'/'0.x' is an abandoned early line; the official modelcontextprotocol/rust-sdk is now at 1.7.0. rmcp publishes NO rust-version (MSRV unverifiable from metadata — must be checked at the exact tag before merge), is fast-moving/pre-1.0-mentality (breaking minors), and pulls chrono in addition to the workspace's HLC/time handling (a second date/time stack). It is tokio-coupled, which is fine (matches workspace tokio 1.44), but the existing hand-rolled mneme-mcp stdio server already works. Reject the loose 0.1/0.x pin.
  - **Fix:** If MCP-SDK adoption is truly wanted: pin rmcp to an EXACT recent tag (e.g. rmcp = "=1.7.0") and CI-gate it on 1.86 before merge (declares no MSRV; verify by compiling). Otherwise KEEP the existing hand-rolled mneme-mcp server (zero new dep, already fail-closed) — this is the recommended path since these plans mark rmcp as deferred/optional anyway. Avoid pulling chrono; if rmcp forces it, accept it only in the off-TCB adapter crate, never in mneme-verify.
- **sharks 0.5 (Heir-Proof Memory seed escrow)** — Security-sensitive + unmaintained + outdated deps. sharks is a Shamir Secret Sharing crate (directly guards a recovery seed) whose last release is 0.5.0 with no commits in years — abandoned for a crypto-critical role. It pulls hashbrown 0.9 (very old) and rand 0.8, and ships an arbitrary 0.4.7 dep. An unmaintained secret-sharing implementation handling key material is exactly the 'security-sensitive' class to reject. (License MIT/Apache is fine; maintenance/age is the problem.)
  - **Fix:** Use vsss-rs (actively maintained, RustCrypto-adjacent, audited Shamir/Feldman/Pedersen VSS, MIT OR Apache-2.0, builds on 1.86) — the plan's own noted alternative. If a heavy dep must be avoided, the plan's fallback of a ~120-line in-crate GF(256) SSS with explicit zeroize is acceptable AND keeps it inside the auditable TCB-adjacent surface. Do not ship sharks.
- **printpdf 0.7 (Consent Vault, MNEME Vault, Heir-Proof, CreditLedger, Journal)** — Justification is materially FALSE, not a build-blocker. Every plan claims printpdf is 'pure Rust, no system libs, leaner than typst.' printpdf 0.7 actually pulls allsorts, usvg, svg2pdf, pdf-writer, image, owned_ttf_parser, and js-sys — a large font/SVG/raster tree, not a lean one. It builds on 1.86 (no MSRV declared, MIT), so it is not rejected for toolchain reasons, but the 'tiny, no-deps' premise behind choosing it over typst is wrong and should be corrected. Also '0.7' is two minors stale (current 0.9.1).
  - **Fix:** Keep PDF generation but fix the rationale and pin: printpdf = "=0.7.0" works, or move to 0.8.x/0.9.x (still MIT, still 1.86). If a genuinely minimal generator is wanted for the fixed one-page certificate/invoice templates, use pdf-writer directly (low-level, tiny, MIT OR Apache-2.0) and drop the SVG/font tree. Stop describing printpdf as 'no system libs / leaner'.

## Build waves
### Wave 0 — Foundation (4.5w)
- **Products:** mneme-receipts, mneme-operator-key, mneme-lineage + mnemed wiring, mneme-verify-wasm, mneme-app-meta, mneme-test-fixtures + CI lane template, mneme-desk-shell, mneme-bundle, mneme-mcp-rmcp (flagged)
- **Depends on:** Existing shipped MNEME (core/crypto/cap/smt/account/store/mnemed). Internal order: receipts -> {operator-key, lineage, wasm, app-meta, fixtures} in parallel -> desk-shell -> bundle. Sub-components overlap; calendar duration ~4.5 wk with 2-3 engineers, not the 8.4 wk serial sum.
### Wave 1 — Receipt-only products (no app, validate the keystone) (4.5w)
- **Products:** Recall Ledger, Portable Brain
- **Depends on:** Wave 0 (mneme-receipts, mneme-verify-wasm, mneme-test-fixtures). Portable Brain also needs mneme-bundle + mneme-brain-mcp (on mneme-mcp-rmcp core). These are CLI/daemon/WASM products with no Tauri shell — they prove mneme-receipts and the bundle/verify path before any app depends on them. Run in parallel.
### Wave 2 — First desktop apps (lowest-complexity Tauri products) (5.5w)
- **Products:** Tamper-Evident Journal, MNEME Vault
- **Depends on:** Wave 0 (mneme-desk-shell, mneme-app-meta, mneme-lineage, mneme-verify-wasm) + Wave 1 (proven mneme-receipts MTL path). Journal = single-operator RFC6962 log over mneme-receipts MTL = thinnest app, validates the shell. Vault = lineage-surfacing second-brain, validates lineage wiring + mneme-mcp-rmcp. Run in parallel; Journal ships first as smoke test of the shell.
### Wave 3 — Capability/consent/legacy apps (build on Wave 2-proven shell + bundle) (7w)
- **Products:** CapGuard, Consent Vault, Heir-Proof Memory
- **Depends on:** Wave 0 + Wave 2 (proven desk-shell) + mneme-bundle (Consent WithdrawalCertificate, Heir HeirBundle) + vsss-rs seed-escrow (Heir). CapGuard adds product-specific Python adapters (CrewAI/AutoGen/LangGraph) — do NOT over-share, single product needs them. These three share cap-issuance/attenuate + consent-revocation + sealed-bundle patterns. Run in parallel.
### Wave 4 — Attribution + P2P (heaviest / most product-specific) (8w)
- **Products:** CreditLedger, Two-Brain Sync
- **Depends on:** Wave 0 + Wave 3-proven app stack. CreditLedger needs mneme-receipts Shapley (ShapleyCertV1) + desk-shell. Two-Brain Sync needs the genuinely product-specific mneme-pair/mneme-peer/mneme-sync-engine over /v1/sync + mdns-sd 0.20 (sync, no async runtime conflict) — built last because the P2P pairing/discovery stack is shared by no other product. Run in parallel.

## First build path
FOUNDATION-FIRST, THEN JOURNAL. Monday: start mneme-receipts (lift crates/mneme-cli/src/mtl.rs + shapley.rs into one off-TCB library crate, re-export mneme-account ROBR/forget-proof, centralize MTL_HONESTY/ROBR_HONESTY/SHAPLEY_HONESTY/§3). This is the verified keystone: 6 of 9 plans are literally blocked on 'make MTL reachable as a library,' the types are binary-private today, and every receipt-construction/verification path depends on it. In parallel, the cheap unblockers: mneme-operator-key (factor the 18×-duplicated load_or_generate_operator), mneme-lineage + the additive RecallEntryJson wiring at mnemed http.rs:86, and mneme-verify-wasm (validate wasm32-on-1.86 once). Then mneme-app-meta (redb =2.6.3 + no-plaintext guard) and the test-fixtures/CI lane, then mneme-desk-shell. FIRST SHIPPABLE PRODUCT = Tamper-Evident Journal: it is the thinnest real app (single-operator RFC 6962 transparency log over mneme-receipts MTL + one-tap WASM proof + the desk-shell), so it exercises receipts, app-meta, lineage, wasm, and the shell end-to-end as a smoke test before any heavier app (Consent/Heir/CapGuard/CreditLedger/Two-Brain) commits to that stack. Path: receipts (1.5w) -> shell+app-meta+wasm+lineage+fixtures (parallel, ~3w) -> Journal (5.2w nominal). A demoable signed-journal-with-offline-proof in roughly 6-7 calendar weeks; everything else then reuses the proven foundation.

## Honesty invariants & cut-lines
CUT-LINES & MSRV HARD STOPS (fail-closed): (1) redb is the only real toolchain-breaker — PIN =2.6.3 everywhere; 3.x/4.x = MSRV 1.89 > 1.86. The Two-Brain 'redb 4.1' pin is a hard build failure; cut it. (2) PIN time =0.3.41 and keyring =3.6.3 — both have newer lines (0.3.49 / 4.x) that require MSRV 1.88 and break on a silent cargo update. (3) CUT sharks (Heir seed escrow): unmaintained crypto guarding a recovery seed — replace with vsss-rs or in-crate GF(256)+zeroize. (4) DEFER rmcp: pin '0.1/0.x' is stale (SDK 1.7.0), no declared MSRV, pulls chrono (2nd time stack). Keep the existing hand-rolled mneme-mcp; only adopt rmcp =1.7.0 if truly needed, 1.86-CI-gated and strictly off-TCB. (5) CORRECT the printpdf rationale in all plans: it is NOT 'lean/pure-Rust/no system libs' (pulls allsorts/usvg/svg2pdf/image); use pdf-writer for the fixed templates if leanness matters. TCB & HONESTY INVARIANTS (never violate): NONE of the new shared crates may import mneme-verify — the 474-line/500-budget verifier TCB stays untouched and all 9 products are off-TCB. Honesty constants (MTL/ROBR/SHAPLEY/§3) live ONLY in mneme-receipts so the insta snapshot guard locks them in one place, not nine; never weaken them. mneme-app-meta's 'no memory plaintext in redb' must be an ENFORCED shared test, not a per-product convention — memory bytes stay in the MNEME store. mneme-crossref must keep zero mneme-* deps. WHAT STAYS UNBUILDABLE (do not let marketing drift): these products prove integrity/provenance/authorization/order — NOT truth (authenticated != true), NOT exact nearest-neighbor, NOT zero-knowledge (commitment_binding is a tagged BLAKE3 envelope; the Schnorr path proves faithful committed-match execution, not a SNARK and not semantic truth). DO-NOT-OVER-SHARE: CapGuard's Python framework adapters and Two-Brain's mneme-pair/peer/sync-engine are genuinely single-product — keep them out of the shared layer. SCHEDULING NOTE: the per-product week estimates (sum 64.6w) are serial-authored; with the foundation built once and 2-3 engineers running each wave's products in parallel, calendar time collapses to roughly Wave0 4.5w + W1 4.5w + W2 5.5w + W3 7w + W4 8w with overlap — order is dependency-correct, the absolute weeks are the standalone-plan figures, not additive calendar time.
